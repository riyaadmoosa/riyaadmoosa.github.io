Mitigate Brute Force Attack

Linode Linux Admin SFTP, SSH

Incident Overview

Security: Brute Force Attack

A user notified us that they were unable to login to our SFTP server. After investigation, we discovered a brute-force attack was being conducted against our SFTP server. It was investigated and stopped.

  • Step 1: Restarted the server thinking this would resolve the issue by clearing any stale connections
  • Step 2: Logged into the server and found it to be quite slow. Looked through different logs. Found in /var/log/auth.log that the server was being attacked using brute-force.
  • Step 3: Also ran the top command and saw that the Fail2Ban service was using the most processes.
  • Step 4: Blocked the offending IP through the UFW firewall
  • Step 5: Checked and saw the brute force was still occurring on port 22. Checked the sSHD config file and saw that the por was open alongside the custome SSH port
  • Step 6: Discussed with manager and he gave permissions to disable port 22. Closed off port 22 in SSD configuration.
  • Step 7: Configured Fail2Ban to ban an IP after 3 failed SSH login attempts within 5 minutes.
  • Step 8: Searched online and saw the IP belonged to an ISP in Europe. I reported the offending IP to them along with an except of the logs. The ISP is in Europe

Results

When the offending IP, was blocked by the security Admin team, then the attack stopped. Wrote a full report for direct line manager and the cybersecurity team as well.

Code Injection on Website

Linux PHP Mail Server

Incident Overview

A user notified us the web site on our custom email marketing platform was not working. When loading the page, it gave an error which pointed to the PHP files.

Architecture & Implementation

  • Step 1: Notified the developer immediately as to the error message and enquired from him if there were any changes made to the code.
  • Step 2: As no changes were made to the code, further investigation continued and discovered the index.php and .htaccess files had new date and time stamps.
  • Step 3: Both files were opened, copied the code that was in there and pasted it into companny managed Microsoft Co-Pilot. This confirmed that the code in those files were malicious and advised to delete them immediately.
  • Step 4: Discussed with manager further. Checked the /etc/passwd file and /home directories and saw that no new users were added.
  • Step 5: Agreed to delete those files and restored the index.php and .htaccess files from a backup.
  • Step 6: Tested on a different browser, logged in and confirmed that the site was working again.
  • Step 7: Notified the users of the site that it was back up again.
  • Step 8: Adjusted the firewall rules to only allow traffic from company VPN as this was where company users would connect from.
  • Step 9: Drafted incident report and sent to manager and cybersecurity team.

Results

Adjusted firewall rules to only allow traffic from company VPN, thus increasing the security of the server.
